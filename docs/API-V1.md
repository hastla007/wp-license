# WP License Captain REST API v1

Base namespace: `/wp-json/wplc/v1`. The machine-readable contract is `docs/openapi-v1.json`.

General rules:

- All requests must use HTTPS.
- All date-time values are UTC in the form `YYYY-MM-DD HH:MM:SS`.
- Every response of this API, including every error, is sent with `Cache-Control: no-store, no-cache, must-revalidate, max-age=0, private`, `Pragma: no-cache` and `Referrer-Policy: no-referrer`. Exclude `/wp-json/wplc/` from page and CDN caches as well.
- Errors are WordPress REST errors: `{"code": "...", "message": "...", "data": {"status": 409, ...}}`. **`code` is the contract.** The `message` is a fixed English text for logs; it is not translated into the shop language and may change. Clients must decide by `code` and show their own, translated text. See [Error codes](#error-codes).
- `429` and `503` responses carry a `Retry-After` header (seconds; also in `data.retry_after`).

## First activation

`POST /activations`

JSON body:

```json
{
  "license_key": "WPLC-...",
  "product_key": "voucher-captain-pro",
  "installation_id": "uuid-v4",
  "installation_secret": "at-least-32-random-characters",
  "site_url": "https://shop.example",
  "environment": "production",
  "product_version": "1.0.0",
  "wp_version": "6.8.0",
  "php_version": "8.2.0"
}
```

| Field | Rule |
| --- | --- |
| `license_key` | Required. Case-insensitive. Everything outside `A-Z`, `0-9` and `-` is ignored and typographic dashes (en dash, em dash, minus, non-breaking hyphen) count as `-`, so a key pasted with line breaks, non-breaking or zero-width spaces or quotes is accepted. |
| `product_key` | Required. `^[a-z0-9_-]{1,100}$` (upper case is folded). Must be the product the license was sold for. |
| `installation_id` | Required. UUID generated by the client; compared in lower case. |
| `installation_secret` | Required. `^[A-Za-z0-9._~+/=-]{32,128}$`. The server validates the value and never rewrites it; any other character (space, `<`, `%`, line break, non-ASCII) is rejected with `400 invalid_activation`. `bin2hex( random_bytes( 32 ) )` or base64 are fine. |
| `site_url` | Required. See [Site address](#site-address). |
| `environment` | Optional, default `production`. Exactly `production`, `staging` or `development`, lower case. Any other value (`Production`, `prod`) is rejected with `400 invalid_activation`; it is never silently treated as `production`. |
| `staging_parent_installation_id` | Required for `staging`: the `installation_id` of an active live activation of the same license. |
| `product_version`, `wp_version`, `php_version` | Optional strings. Stored up to 30 characters; longer values are cut. Arrays or objects are rejected with `400 rest_invalid_param`. |

The client generates and keeps the installation ID and secret. The server stores a SHA-256 verifier and an AES-256-GCM encrypted copy of the secret. The complete license key is not stored in plaintext.

`400 invalid_activation` lists the rejected fields in `data.fields`, for example `{"code":"invalid_activation","data":{"status":400,"fields":["installation_secret","environment"]}}`.

### Environments and limits

- **production**: counts against the live-site limit of the license (`site_limit`). Over the limit: `409 site_limit` with `data.site_limit` and `data.site_count`.
- **staging**: one staging site per live activation, free of charge, linked through `staging_parent_installation_id`. The host of the staging site must be plausible for a copy of the live site: the same registrable domain as the live site (`staging.example.com` for `www.example.com`, also a subdirectory), a local host, a host with a staging label (`staging`, `stage`, `stg`, `dev`, `test`, `testing`, `preprod`, `preview`, `sandbox`, `uat` as one of its labels) or a staging domain of a hosting provider (`*.wpengine.com`, `*.kinsta.cloud`, `*.pantheonsite.io`, ...). **A staging request for any other host is not refused but counted as a live site**: the activation is stored with `environment: production`, uses a live slot (or fails with `409 site_limit`, `data.requested_environment: staging`), and the signed response says `"environment": "production"`. Clients should show the returned `environment`. Shop owners can extend the rule with the filter `wplc_is_staging_host` (and `wplc_registrable_domain`). A second staging site: `409 staging_limit`.
- **development**: does not use a live slot. Only for local hosts: `localhost`, single-label names, `*.localhost`, `*.test`, `*.local`, `*.internal`, `*.lan`, `*.home.arpa`, `*.localdomain`, `*.ddev.site`, `*.lndo.site`, loopback, private (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`) and link-local addresses; otherwise `400 development_site_invalid` (filter `wplc_is_local_development_url`). The number of active development activations per license is capped at twice the live-site limit, at least 5 (filter `wplc_development_site_limit`); beyond it `409 development_limit` with `data.development_limit` and `data.development_count`. Unused development sites can be released in the customer account, the admin, through `DELETE`, or with `wp wplc activation release --license=<id> --environment=development`.

A license that grants no access cannot be activated: `403 license_expired` (paid period and grace period over), `403 license_suspended`, `403 license_revoked`, or `403 license_inactive` (any other state, for example `pending`); `data.license_status` carries the status. A license inside its renewal grace period can still be activated.

### Signed data (`EntitlementData`)

The same object is returned by `POST /activations` and `POST /entitlements/check`.

| Field | Meaning |
| --- | --- |
| `activation_id` | ID of the activation; used in `DELETE /activations/{activation_id}`. |
| `installation_id` | The installation the data is for. |
| `activation_status` | `active` or `deactivated` (see [Released installations](#released-installations)). |
| `product_key` | Product the license was sold for. A client must reject data whose `product_key` is not its own. |
| `license_status` | See [Status values](#status-values). |
| `access` | `true` when the license grants its rights right now. This is the field to decide by; it already includes the grace period. |
| `paid_until` | End of the paid period; `null` for a license without an end. |
| `access_until` | Time at which `access` ends if nothing changes: `paid_until`, or `grace_until` when a grace period applies. `null` without access and for a license without an end. |
| `grace_until` | End of the renewal grace period (14 days after `paid_until`) when one applies to this license: automatic renewal is on, or the license is `past_due`. Otherwise `null`. The license is *inside* its grace period when `server_time >= paid_until` and `access` is `true`. |
| `site_limit`, `site_count` | Live-site limit and number of active live activations. |
| `environment` | `production`, `staging` or `development` as stored by the server (see above for staging requests that count as live). |
| `staging_parent_id` | `activation_id` of the live site of a staging activation, else `null`. |
| `entitlements` | Feature rights by key; empty without access. |
| `site_match` | Only when the request carried `site_url` (`/entitlements/check`): `false` when the client runs on another address than the activated one. |
| `deactivated_at` | Only for a released installation. |
| `server_time` | Server clock when the answer was signed. |
| `cache_expires_at` | Until then the client may rely on this snapshot without reaching the server: `server_time` + 14 days, **but never later than `access_until`**. See [Offline use](#offline-use-and-cache_expires_at). |

### Status values

`license_status` is one of:

| Value | Meaning | `access` |
| --- | --- | --- |
| `active` | Paid and usable. | `true` |
| `past_due` | An automatic renewal failed or is pending. | `true` until `grace_until`, then `false` |
| `expired` | The paid period and any grace period are over. Also reported for an `active` license whose paid period ended before the daily job ran. | `false` |
| `suspended` | Blocked by the shop, for example after a payment dispute; can become `active` again. | `false` |
| `revoked` | Ended for good (refund). | `false` |
| `pending` | Not issued completely yet. | `false` |
| `deactivated` | Not a state of the license but of this installation: its activation was released. | `false` |

### Offline use and `cache_expires_at`

A client may keep the last verified snapshot (the `payload` string with its signatures) and use it while the server cannot be reached. The snapshot is valid until `cache_expires_at`; after that the client must treat the license as without access until it receives a new signed answer. Because `cache_expires_at` never exceeds `access_until`, a site that blocks the license server cannot outlast the paid time, and an honest site in the grace period is not locked out early. The client must take the deadline from the signed `cache_expires_at` of the snapshot it stores; it must not restart a local timer on every successful request, and it must not cap the time at `paid_until` on its own. The maximum offline window is 14 days (filter `wplc_offline_cache_days` on the server).

### Response signatures

Every signed response carries these members:

| Member | What it is |
| --- | --- |
| `payload` | The exact JSON text the server signed: an object with the members `data` and `nonce`. `nonce` echoes the `X-WPLC-Nonce` header of an authenticated request; for `POST /activations`, which is not HMAC-authenticated, it is the `installation_id` of the request. |
| `payload_signature` | Lowercase hex HMAC-SHA-256 over `payload` exactly as transmitted, keyed by the installation secret. |
| `payload_signature_ed25519` | Base64 Ed25519 signature of the server over `wplc-response-v2\n{installation UUID, lower case}\n{payload}`. Covers the nonce, so a recorded answer cannot be replayed for a later request. Present when the server has a signing key. |
| `key_id` | First 16 hex characters of the SHA-256 of the signing public key. |
| `data`, `signature` | **Legacy.** `data` repeats `payload.data`; `signature` is the HMAC-SHA-256 over the server's JSON encoding of `data` (`JSON_UNESCAPED_SLASHES`). Not bound to a request. |
| `signature_ed25519` | **Legacy.** Ed25519 signature over `wplc-response-v1\n{installation UUID, lower case}\n{JSON of data}`. Not bound to a request. |

A client must verify, in this order:

1. `payload_signature` against the HMAC of the received `payload` string, in constant time.
2. `payload_signature_ed25519` against the pinned public key of the server (`wp wplc signing-key --field=public_key`), over `wplc-response-v2\n{own installation UUID}\n{payload}`. A client that pins a key must reject a response, and a cached snapshot, without a valid signature.
3. JSON-decode `payload`, require `nonce` to equal the value sent with this request, and use `payload.data`. Never read the top-level `data`, and never run the Ed25519 check over the top-level `data`: only the bytes of the verified `payload` are trustworthy.

The HMAC proves integrity in transit and of the client's cache, but the client knows the installation secret itself. Only the Ed25519 signature proves that this license server produced the answer.

**Legacy fields.** `data`, `signature` and `signature_ed25519` are still sent so that product builds with an older bundled client keep working; the server will keep sending them for the whole of API v1. They are the only downgrade path: a client that accepts `data` + `signature` when `payload` is missing can be fed a stripped, replayed answer. New clients must require `payload`, `payload_signature` and (with a pinned key) `payload_signature_ed25519` and must ignore the legacy members. Removing the fallback from the bundled `LicenseClient` is tracked as B-158.

- `payload_signature_ed25519` for payload `{"data":{"license_status":"active"},"nonce":"0123456789abcdef"}`: `7JE5lIc5ZSbbYP1HFGvM1+wM5pnjhI/yZTaZUlmhgd+JcmXTzNi8hWvj7wTqDEjBfaDYlMyON3tB4A1ey3reBg==`

#### The server's signing key

Set `WPLC_RESPONSE_SIGNING_KEY` in `wp-config.php` on a production server (`wp wplc signing-key --generate` prints a value and its public key). It is the base64 of a 32-byte seed or of a 64-byte Ed25519 secret key. A value that is not a real key (wrong length, not base64, a 64-byte value whose halves do not belong together) is **not used**: responses are then sent without the Ed25519 members, `wp wplc signing-key` ends with an error that names the reason, and the action `wplc/response_signing_key_unavailable` fires. Without the constant the server creates a key once and stores it encrypted in the option `wplc_response_signing_key`; see `docs/SECURITY-OPERATIONS.md` for what happens when that key is lost. The Ed25519 members are also omitted when PHP has neither sodium nor WordPress' sodium_compat.

### Site address

`site_url` must be an `http` or `https` URL without credentials, query string or fragment. Rules of the normalization (the stored form):

- No whitespace or control characters anywhere; valid UTF-8 only.
- Host in lower case, trailing dot removed, internationalized names as punycode (also on servers without the PHP extension `intl`), IPv6 in compressed form. A host that ends in a number but is not a dotted-quad IPv4 address is rejected (`0x7f.1`, `2130706433`, `192.168.001.010`).
- Default ports are dropped.
- Path: duplicate and trailing slashes removed; `.` and `..` segments rejected; percent-escapes of unreserved characters decoded, other escapes in upper case, non-ASCII characters percent-encoded.
- At most 255 bytes.

Whether two addresses are **the same site** is decided by a comparison key that additionally ignores the scheme, a leading `www.` and the case of the path. `http://www.example.com/Shop` and `https://example.com/shop` are the same site; `https://shop.example.com` and `https://example.com` are not.

### Activating the same site again

The client keeps its installation ID and secret in one option. If valid credentials are already stored, `LicenseClient::activate()` first calls `/entitlements/check` and returns that result instead of creating a second activation; pass `true` as the fourth argument (`$force`) to request a new activation regardless.

Repeating `POST /activations` with a known `installation_id`, the same secret and the same license is idempotent and returns the current data. A changed `site_url` is stored (audit action `site_url_changed`); a staging activation cannot move to a host that is unrelated to its live site (`409 staging_site_invalid`). Another secret or license: `409 installation_conflict`. A released installation ID: `409 activation_deactivated`; the client must generate a new installation ID.

When a **new** installation ID activates the same site (same comparison key, same environment) as an existing active activation of the same license (lost options, database restore, migration, switch to HTTPS), the server replaces the old activation instead of counting a second site:

1. The limits are checked first, without the activation that would be replaced. A request over the limit changes nothing.
2. The new activation is stored.
3. Only then the old one is deactivated (audit action `site_replaced`). If the new activation cannot be stored, the old one stays active.
4. The staging site of a replaced live site is not released: it is linked to the new live activation (audit action `staging_reparented`).

The old credentials then get signed `deactivated` answers. Possession of the license key authorizes the replacement. Development activations are never replaced this way: `http://localhost:8888` is a different machine for every developer.

Deactivating a live site, whether through this API, the customer account, or the admin, also deactivates the staging site linked to it.

## Authenticated requests

For every request after activation, send:

- `X-WPLC-Installation-Id`: installation UUID (compared in lower case)
- `X-WPLC-Timestamp`: Unix timestamp in seconds
- `X-WPLC-Nonce`: unique random value, 16–80 URL-safe characters
- `X-WPLC-Signature`: lowercase hex HMAC-SHA-256

The signature input is UTF-8 text joined by newline characters:

```
UPPERCASE_METHOD
REST_ROUTE
TIMESTAMP
NONCE
SHA256_OF_RAW_REQUEST_BODY
```

`REST_ROUTE` is the route without the `/wp-json` prefix and without a query string, for example `/wplc/v1/entitlements/check`. Because only the body is signed, parameters of signed requests belong in the JSON body, not in the query string.

Order of the checks and their answers:

| Check | Answer |
| --- | --- |
| Headers malformed or missing | `401 invalid_request_signature` |
| Timestamp more than five minutes off | `401 request_expired`; `data.server_time` is the Unix time of the server, so a client can detect a wrong clock |
| Installation ID unknown | `401 activation_not_found` |
| Stored credential unreadable | `401 installation_secret_invalid` |
| Signature wrong | `401 invalid_request_signature` |
| More than 120 requests per installation and minute | `429 rate_limited` |
| Nonce already used within ten minutes | `409 request_replayed` |
| Limit or replay store unavailable | `503 rate_limit_store_unavailable`, `503 replay_store_unavailable` |
| Activation was released | signed refusal, see below |

Requests that fail before the nonce check do not consume the nonce.

### Released installations

An installation whose activation was released (by the customer in the account, by the admin, by `DELETE`, by a replacement, or together with its live site) is still recognized and its signature is still checked. It gets a **signed** answer instead of an anonymous `401`, so it cannot keep running on a cached "active" snapshot:

- `POST /entitlements/check` answers `200` with signed data: `activation_status: "deactivated"`, `license_status: "deactivated"`, `access: false`, empty `entitlements`, `deactivated_at`.
- `DELETE /activations/{activation_id}` answers `200` with the signed confirmation `{"activation_id": ..., "status": "deactivated"}` again, so a client can always clear its local credentials.
- Every other signed route (`POST /updates/check`) answers `403 activation_deactivated`; `data.signed` contains a complete signed envelope with the same data as the entitlement check. Its nonce is the nonce of the refused request.

A client that verifies such an answer must drop its cached rights and its stored credentials. To use the license again it activates with a new installation ID. `401 activation_not_found` remains for installation IDs the server does not know (never activated, or deleted by the retention rules long after the release); a client must not treat an unsigned `401` as proof that the license ended.

## Entitlement check

`POST /entitlements/check`

Optional JSON body: `product_version`, `wp_version`, `php_version` (stored up to 30 characters; an omitted or empty value keeps the stored one) and `site_url`.

When the client sends its current `site_url`, the signed data contains `site_match`: `true` when it is the activated site (comparison key, see [Site address](#site-address)), `false` when the installation runs under another address, for example a copy of the site that carries the copied credentials. The server does not refuse such a request yet; it fires the action `wplc/activation_site_mismatch`. Clients should send `site_url` and treat `site_match: false` as "this copy is not the activated site".

The response is `EntitlementData` as described above. `404 license_not_found` means the license row of the activation is gone.

## Deactivation

`DELETE /activations/{activation_id}` (authenticated)

Optional JSON body: `{"site_url": "https://shop.example"}`. When `site_url` is sent it must be the activated site (comparison key); otherwise the server answers `409 site_mismatch` and deactivates nothing. This keeps a copy of a site (staging clone with the copied credentials) from ending the activation of the original. Clients should always send their current address and, on `site_mismatch`, only remove their local credentials.

`403 activation_mismatch`: the path does not name the activation of the signing installation. Success and repeated calls: `200` with signed `{"activation_id": 123, "status": "deactivated"}`.

## Update check and download

`POST /updates/check` (authenticated), JSON body `{"product_key": "...", "current_version": "1.2.3"}`. Both fields are required strings; a missing or non-string field is rejected with `400 rest_missing_callback_param` or `400 rest_invalid_param` *before* the request is authenticated.

Signed `data`:

| Case | Data |
| --- | --- |
| No release is published for the product | `{"update_available": false, "reason": "package_unavailable"}` |
| The reported version is the newest | `{"update_available": false, "current_version": "<as reported>"}` |
| Update available | `update_available: true`, `product_key`, `version`, `package_url` (one-use URL of `GET /updates/download/{token}`), `sha256` (lowercase hex of the ZIP), `requires_php`, `requires_wp`, `tested_wp`, `release_notes` (HTML, filtered with `wp_kses_post`), `download_expires_at` (UTC, ten minutes after the check) |

Errors: `403 license_inactive` (the license grants no access or belongs to another product), `403 activation_deactivated` (see above), `503 package_configuration_invalid` (the release has no trusted HTTPS URL or checksum), `503 download_token_error`.

`GET /updates/download/{token}` is not authenticated; the token is the credential. It consumes the grant and redirects (`302`) to the package. An unknown, expired or used token, a license without access, or an untrusted package host is answered with `404` **without a body**. A path that is not 64 lowercase hex characters does not match the route; WordPress then answers `404` with the JSON error `rest_no_route`. `GET /packages/{token}` (stream of a locally stored package) behaves the same way.

The product client must verify the signatures of the metadata and the SHA-256 of the ZIP before installation.

| `development_site_invalid` | 400 | activations | `environment: development` on a host that is not local. |
| `staging_parent_required` | 400 | activations | `environment: staging` without a valid `staging_parent_installation_id`. |
| `rest_missing_callback_param` | 400 | all | A required parameter is missing (WordPress). |

| `invalid_key` | 401 | activations | The license key is unknown. Ask the user to check the key. |
| `invalid_request_signature` | 401 | signed | Authentication headers missing, malformed or wrong. |
| `request_expired` | 401 | signed | Timestamp outside five minutes; compare the clock with `data.server_time`. Not a license problem. |
| `activation_not_found` | 401 | signed | The installation ID is unknown to the server. Activate again. |

| `license_not_found` | 404 | entitlements | The license of the activation no longer exists. |
| `site_limit` | 409 | activations | No live slot left; `data.site_limit`, `data.site_count`. Offer to release a site or upgrade. |

| `development_limit` | 409 | activations | Too many development activations; `data.development_limit`, `data.development_count`. |
| `staging_parent_invalid` | 409 | activations | The named live activation is not an active live site of this license. |
| `staging_site_invalid` | 409 | activations | A staging activation tried to move to a host unrelated to its live site. |
| `installation_conflict` | 409 | activations | The installation ID exists with another secret, license or environment. Generate a new one. |

| `site_mismatch` | 409 | deactivation | The `site_url` of the request is not the activated site; nothing was deactivated. |
| `deactivation_failed` | 409 | deactivation | The activation changed at the same moment. Retry. |
| `request_replayed` | 409 | signed | The nonce was already used. Retry with a new nonce. |

| `activation_failed` | 500 | activations | The server could not read or write the activation. Retry. |

| `replay_store_unavailable` | 503 | signed | The replay storage failed; the request was refused. Retry. |
| `package_configuration_invalid` | 503 | updates | The release is misconfigured on the server. |
| `download_token_error` | 503 | updates | The download grant could not be stored. Retry. |

Rule for clients: only a **signed** answer may take rights away (`access: false`, `license_status`, `activation_status: deactivated`, or `activation_deactivated` with `data.signed`). Every unsigned error (`4xx` without `data.signed`, `5xx`, timeouts, HTML from a firewall) leaves the cached snapshot in force until its `cache_expires_at`.

`activation_deactivated` is the only code that occurs with two statuses (403 on signed routes, 409 on `POST /activations`); every other code has exactly one. The Stripe webhook route uses its own codes (`wplc_stripe_*`, see `docs/STRIPE-WEBHOOKS.md`).

## Rate limits behind a proxy or CDN

Activation requests are limited in two ways:

- **Per license-key prefix** (the first 13 characters of the normalized key): 20 attempts per minute, counted for every request with that prefix, so one key cannot be tried from many addresses.
- **Per client address** (IPv6: per /64): 30 **failed** attempts per minute. Only requests that fail before the key is verified count (malformed request, unknown key). A valid key is never blocked by the failures of other clients behind the same address (shared hosting, NAT, a CDN without proxy configuration). A request whose address cannot be determined is counted in one shared bucket.

Exceeding either returns `429 rate_limited`. The buckets are stored as HMAC-SHA-256 with a server-side key (`WPLC_RATE_LIMIT_KEY` in `wp-config.php`, otherwise derived from the WordPress auth salt), so the table does not contain reversible hashes of addresses, key prefixes or installation IDs.

By default the address is `REMOTE_ADDR`. Behind a reverse proxy or CDN that is the proxy, so all customers would share one bucket. Configure the forwarding header in `wp-config.php`:

```php
define( 'WPLC_TRUSTED_PROXY_HEADER', 'HTTP_CF_CONNECTING_IP' ); // or 'HTTP_X_FORWARDED_FOR'
define( 'WPLC_TRUSTED_PROXIES', array( '173.245.48.0/20', '2400:cb00::/32' ) ); // addresses of your proxies
```

- The header is used only when `REMOTE_ADDR` matches an entry of `WPLC_TRUSTED_PROXIES` (single IPs or CIDR ranges, IPv4 and IPv6). IPv4-mapped IPv6 entries such as `::ffff:10.0.0.0/104` are understood as their IPv4 range (`10.0.0.0/8`).
- For a list header such as `X-Forwarded-For` the right-most address that is not a trusted proxy is used; anything further left is supplied by the client and ignored.
- If `WPLC_TRUSTED_PROXIES` is not defined, the header is trusted from every peer. That is only safe when the origin server cannot be reached directly (firewall restricted to the proxy); otherwise anyone can send the header and choose their own bucket. With `X-Forwarded-For` and no proxy list the right-most entry is used, which is correct for exactly one proxy in front of the origin.
- The filter `wplc_client_ip` receives the resolved address (or an empty string) for custom setups.

Rejected requests are counted per error code and UTC day (`\WPLC\Api\V1\ApiLog::counts()`, kept two days) and written to the WooCommerce log `wplc-api` (the first 20 per code and day, then every hundredth). The log contains the code, status, method and route, never an address, key or site.

## Credential rotation and recovery

Installation secrets are encrypted in a versioned envelope (`v1:<key-id>:<base64>`). Configure a key ring in `wp-config.php` before activating this release:

```php
define( 'WPLC_INSTALLATION_ENCRYPTION_KEYS', array(
	'2026-01' => getenv( 'WPLC_INSTALLATION_KEY_2026_01' ),
	'2026-06' => getenv( 'WPLC_INSTALLATION_KEY_2026_06' ),
) );
define( 'WPLC_INSTALLATION_ENCRYPTION_KEY_ID', '2026-06' );
```

Keep the previous key in the ring while ciphertexts still refer to its key ID. New writes use the configured current ID; reads select the matching key. Legacy unversioned ciphertext is still read using configured keys and, as a fallback, the historical WordPress `secure_auth` salt. Rotate existing activation rows with `wp wplc rotate-installation-secrets` (dry run by default, all rows; `--apply` to write). The command also re-encrypts the stored response signing key and **ends with exit code 1 as long as any row still uses an old key**. Remove an old key only after a run that ends with exit code 0 and a restore test. Details and the multisite note: `docs/SECURITY-OPERATIONS.md`. Never commit real key values.

License keys carry a `license_key_secret_id` in the license row. Configure a key ring in `wp-config.php` and retain every key ID still referenced by a license:

```php
define( 'WPLC_LICENSE_KEY_SECRETS', array(
	'legacy' => getenv( 'WPLC_LICENSE_KEY_LEGACY' ),
	'2026-06' => getenv( 'WPLC_LICENSE_KEY_2026_06' ),
) );
define( 'WPLC_LICENSE_KEY_ID', '2026-06' );
```

The schema migration assigns existing rows the key ID `legacy`. Set that entry to the exact secret previously used for those keys (the historical `WPLC_LICENSE_KEY_SECRET` or auth salt); missing secrets prevent the customer portal from re-deriving the display value, although stored key hashes remain verifiable. To check a candidate recovery ID without changing data, run `wp wplc recover-license-key-ids --to=<key-id>`; after reviewing counts and taking a tested backup, pass `--apply`. A row changes only if deriving its key with that configured ID reproduces its stored SHA-256 verifier. The command inspects all rows and ends with exit code 1 while unverifiable or uninspected rows remain.
